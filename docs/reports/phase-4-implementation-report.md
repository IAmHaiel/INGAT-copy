## Overview

Phase 4 adds a **TimeAndApproval** mode for Goal buckets. Senders can now mark a deposit as requiring their explicit approval before the receiver can withdraw the Goal bucket — even after the standard `unlock_date` has passed. If the sender does not respond within 7 days, a grace period auto-release kicks in.

## Files Added (8 new files)

### 1. `contracts/ingat-vault/src/release.rs` (new — 121 lines)
The core module implementing the condition unlock feature.

**Public API:**
- `request_release(env, receiver, bucket_id)` — Receiver calls after `unlock_date`. Creates a `ReleaseRequest` with `status: Pending` and `grace_period_ends_at: now + 7 days`. Rejects if bucket is not `approval_required`, if called before `unlock_date`, or if a pending request already exists.
- `approve_release(env, sender, receiver, bucket_id)` — Sender approves a pending release request. Sets status to `Approved`. Auth-scoped to the bucket's sender. Rejects if no active request or if bucket is not `approval_required`.
- `can_withdraw_goal(env, bucket, receiver, bucket_id)` — Helper called by `withdraw_goal` and `withdraw_goal_sender`. For TimeOnly buckets (`approval_required = false`): checks only `unlock_date`. For TimeAndApproval: checks `unlock_date` + (approval status is `Approved` OR current time >= `grace_period_ends_at`).
- `get_release_request(env, receiver, bucket_id)` — Read-only query returning the `ReleaseRequest` state.

**Constants:** `GRACE_PERIOD_SECS = 7 * 24 * 3600` (604,800 seconds = 7 days)

## Architecture Decisions

1. **Grace period as an explicit check, not a separate function** — `can_withdraw_goal` evaluates the grace period inline rather than requiring a separate `execute_auto_release` call. This keeps the withdraw flow simple: the caller just calls `withdraw_goal` and the contract determines whether the release condition is met.

2. **No `deny_release` function** — Per spec, the sender's only options are silence (auto-releases) or `approve_release` (immediate release). There is no way to permanently block a release, honoring the non-negotiable auto-release guarantee.

3. **Frontend toggle defaults to `false`** — The approval toggle is off by default, preserving backward compatibility with all existing deposits. Existing buckets created before Phase 4 are TimeOnly and unaffected.

4. **State leases** — All `ReleaseRequest` storage uses `extend_ttl` (10,000 ledgers) matching the pattern used by `BucketState` and `EmergencyRequest`, preventing premature state expiration.
